# Paradox Ticket system design

Paradox Ticket treats a seat as a scarce, short-lived resource. A seat is never considered available from a client-side flag alone: availability is calculated from confirmed bookings plus active holds. A hold stores its seat ids, owner, show, creation time, and `expires_at`; the default time-to-live is ten minutes. Every read removes expired holds before building the seat map, so abandoned checkout becomes available immediately even if a scheduled worker is delayed. A periodic sweeper can perform the same cleanup in production and emit waitlist events.

The hold endpoint is one transactional service operation. In Postgres, it locks the requested seat rows in a stable order, removes expired holds, checks confirmed bookings and active holds, and inserts the new hold before committing. A unique constraint over the show/seat resource for active reservations provides a second line of defence. If two customers request the same seat at once, row locking serialises the requests; the first transaction commits and the second receives a clean conflict response with a refreshed map. The demo API mirrors this invariant in its service layer and returns `409` when an occupied seat is requested.

The frontend subscribes to seat freshness through refetch-on-entry and short polling. A production deployment can replace polling with Postgres change notifications or a WebSocket channel. The client never treats a successful hold as permanent: it displays the server expiry timestamp, updates the countdown locally, and invalidates the seat query after expiry or checkout.

Checkout confirms a hold, rather than accepting raw seat ids. The service re-checks that the hold exists, belongs to the current session, and has not expired. It then creates a booking and booking-seat records in one transaction, marks the held seats confirmed, and deletes the hold. Payment is represented as a strategy (`online` or `venue`) so a pay-at-venue booking is explicit instead of being confused with an unpaid abandoned checkout. Food items are attached to the booking total and can later map to an inventory table.

Every booking receives a stable human-readable reference. The QR payload contains that reference, which is sufficient for venue scanning while the scanner resolves current booking status server-side. Confirmation email delivery is an outbox-style side effect: the booking commits first, then a worker sends a branded message with the QR image. Retries are idempotent by booking reference, so a mail provider retry cannot create a second booking.

Waitlists are scoped by show and seat category and preserve queue position. A cancellation or expired hold triggers a transaction that selects the next eligible entry, creates a short-lived offer, and records its expiry. The offer email contains a signed claim token that identifies the offer but does not grant access to another account. Claiming an offer reuses the normal hold and checkout path with the offer id attached. If the offer expires, the sweeper marks it lapsed and advances to the next queue entry. This prevents silent seat loss while ensuring a customer cannot claim the same released seat twice.

Role checks belong in the service layer, not only in navigation. Customer endpoints are scoped to the authenticated customer; organiser queries are scoped to shows they own; admin mutations cover users, venues, seat layouts, and categories. The current review build exposes the role-specific screens and demo data, while a production adapter can connect the same contracts to managed authentication, Postgres row-level security, Resend email, and a scheduler without changing the customer-facing flows.
